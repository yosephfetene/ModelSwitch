# Proposed Data Model

Conceptual model only. Choose exact SQL types, constraints, migrations,
and indexes during implementation.

## `client_api_keys`

Implemented in `migrations/` (Stage 1):

-   `id` --- UUIDv7 primary key, generated by PostgreSQL
-   `name` --- operator-assigned label, 1--64 characters
-   `key_prefix` --- first characters of the key (for example
    `ms_dev_7Hq2`), for display only
-   `key_hash` --- unique SHA-256 hash of the full key (32 bytes)
-   `created_at`, `revoked_at`
-   `expires_at` --- optional; NULL means the key never expires
    (ADR-033)
-   `monthly_budget_usd` --- optional exact limit per calendar month
    (UTC); NULL means no budget. Spending is not stored: it is the sum
    of the key's `estimated_cost` this month (ADR-035)
-   Status is derived: revoked when `revoked_at` is set, otherwise
    expired once `expires_at` has passed, otherwise active (ADR-022).
    An optional `rate_limit_policy_id` arrives later. Until a key can
    have its own policy, every key shares the configured limits (ADR-031, ADR-032).

Keys are `ms_dev_` or `ms_live_` followed by 32 random bytes in base62.
Generate keys securely, display a new key once, and never log its
plaintext value. A fast hash is sufficient because keys are
high-entropy (ADR-012).

## `request_records`

Implemented in `migrations/` (Stage 1, ADR-027). One row per request
that reached a provider; requests rejected before that get none.

-   `id` --- gateway request ID (`req_` + UUIDv7, time-sortable)
-   `client_request_id` --- nullable, validated client correlation ID
-   `client_api_key_id` --- references `client_api_keys`
-   `requested_model` --- alias or `provider/model` pin as sent
-   `selected_provider`, `selected_model` --- what actually ran
-   `status` --- succeeded, failed, timed_out
-   `error_kind` --- request, status, invalid_response, blocked; set
    only when failed
-   `error_code` --- nullable provider short code (for example
    `rate_limit_exceeded`, `SAFETY`), never a message
-   `provider_status` --- nullable provider HTTP status
-   `latency_ms`
-   `reported_input_tokens`, `reported_output_tokens`,
    `reported_total_tokens` --- nullable provider facts (bigint)
-   `usage_source` --- provider_reported, unavailable
-   `created_at` (start), `completed_at` (insert time)
-   `estimated_cost` --- nullable exact USD estimate: reported tokens
    × the price in effect when the request started. Null means unknown:
    no price, or incomplete usage. It covers only the attempt that
    answered, so it runs low if failed attempts were billed (ADR-034).
-   `pricing_version` --- the `pricing_versions` row used; set exactly
    when `estimated_cost` is
-   Later: `routing_policy_version`, `routing_reason` (with routing
    policies)

Prompts and completions are never stored. If that is ever added, define
opt-in, access controls, retention, and deletion behavior first.

Missing usage stays null with `usage_source = unavailable`; it is never
fabricated. Budgets count only `estimated_cost`, so no estimated token
columns exist (ADR-035).

### Accounting failures

When generation succeeds but this record cannot be written, the failure
cannot be recorded in the row itself. It is captured instead by a
structured `accounting_write_failed` log entry with the request ID, the
`accounting_failures_total` metric, and the
`X-ModelSwitch-Accounting: failed` response header (ADR-009). If an
optional background retry later writes the row, it is marked with
`recorded_late = true`.

## `request_attempts`

Implemented in `migrations/` (Stage 2, ADR-029). One row per provider
call, written in the same transaction as its request record.

-   `request_id`, `attempt_number` --- primary key; the first call is 1
-   `provider`, `model`
-   `status` --- succeeded, failed, timed_out
-   `error_kind`, `error_code`, `provider_status` --- as in
    `request_records`; short identifiers, never provider messages
-   `error_class` --- transient, target_problem, request_problem; null
    on success (ADR-028)
-   `retry_decision` --- what happened next: not_retried, retry,
    fallback, exhausted
-   `latency_ms` --- the call itself, without backoff waits

This separates one logical request from individual provider attempts.

## `routing_policies`

-   `id`, `name`, `version`, `status`
-   validated rule configuration
-   `created_at`, `created_by`

Policy changes should be auditable and validated before activation.
Model aliases start in configuration files; whether they move into the
database is decided with routing policy storage.

## `pricing_versions`

Implemented in `migrations/` (Stage 3):

-   `id`, `provider`, `model`
-   `input_usd_per_million`, `output_usd_per_million` --- exact numerics
-   `effective_from`, `effective_to` --- in effect from the first up to,
    not including, the second; null means current, and each model has
    at most one current price
-   `source_reference`, `retrieved_at`

Pricing changes over time. `modelswitch pricing set` closes the old row
and adds a new one, so old estimates remain explainable (ADR-034).

## Index candidates

-   `request_records(created_at)`
-   `request_records(client_api_key_id, created_at)`
-   `request_records(status, created_at)`
-   `request_attempts(request_id, attempt_number)`
-   `client_api_keys(key_hash)` --- unique, used on every request

Finalize indexes based on query patterns. Define retention and deletion
for related records.

## Consistency notes

-   Use transactions for related record changes where appropriate.
-   Never hold a database transaction open during a provider call.
-   Use atomic database operations for cross-instance budgets and rate
    limits.
-   A database failure after successful generation must not cause
    duplicate generation (ADR-009).
